# Intelligent CRM Agent architecture

## Current topology

FastAPI compiles one Deep Agents supervisor and exactly one registered CRM data subagent at startup.

```text
Authenticated request
└── main agent
    ├── conversation memory tools
    └── crud-agent
        ├── select_{leads,accounts,contacts,opportunities,activities}
        ├── select_account_overview
        ├── insert_{lead,account,contact,opportunity,activity} -> pending action
        ├── update_{lead,account,contact,opportunity,activity} -> pending action
        └── convert_lead -> one atomic pending action
```

Deep Agents' implicit general-purpose subagent is disabled with a harness profile. The `task` tool visible to the supervisor is Deep Agents' native dispatch mechanism; it receives the complete definition generated by `crud_agent/definition.py`.

## Trust boundary

`CRMContext` is created only after HttpOnly Cookie authentication. It contains server-derived `user_id`, role, permissions, conversation ID, and request ID. None of these values are accepted from the chat body or tool arguments.

The data tool performs a permission check, then calls `CRMRepository`, which performs the same permission and owner/all visibility filtering again. The LLM never receives a generic SQL tool and cannot choose an owner or assignee ID. A sales user also cannot attach a record to another salesperson's account, contact, lead, or opportunity by guessing its UUID.

Every `insert_*`, `update_*`, and `convert_lead` tool only creates an idempotent row in `crm_pending_actions`. The approve endpoint locks that action, rechecks the current account's permission and row scope, validates the real table schema, ownership chain, and foreign keys, performs an optimistic concurrency check, and commits the business rows, conversion mapping, audit event, and approval state in one transaction. `convert_lead` never decomposes a conversion into partially approved writes.

## Source ownership

```text
app/agents/
├── main_agent/
│   ├── agent.py       # create_deep_agent and registered subagent specs
│   ├── prompt.py      # supervisor rules
│   └── tools.py       # current-conversation memory only
├── crud_agent/
│   ├── definition.py  # complete subagent definition
│   ├── prompt.py      # data-agent rules
│   └── tools.py       # five-entity CRUD plus conversion and 360° overview (17 tools)
├── context.py         # authenticated runtime identity
├── registry.py        # exactly one enabled subagent
├── service.py         # per-conversation lock and total timeout
└── types.py           # Deep Agents definitions and filesystem permissions
```

Skills are copied into the StateBackend virtual filesystem on each turn. Permissions are fail-closed:

- the supervisor may read `/skills/supervisor/**` and the current conversation memory file;
- `crud-agent` may read only `/skills/crud-agent/**`;
- `crud-agent` is denied `/memory/**`, other Skill roots, and every undeclared virtual path;
- neither Agent receives access to the host project directory or runtime secret files.

## Adding a tool or specialist

1. Create a narrow typed tool; never add arbitrary SQL execution.
2. Derive identity and authorization only from `ToolRuntime[CRMContext]`.
3. Add a Repository method that independently applies role and row scope.
4. Route writes through pending action, transaction, idempotency, optimistic concurrency, and audit logic.
5. Add or update the Agent's Skill under its declared root.
6. Register the definition explicitly and add permission, cross-account, and tool-boundary tests.

The application exposes exactly one data subagent. Additional specialists must be registered explicitly and receive the same fail-closed filesystem and authenticated runtime boundaries.
